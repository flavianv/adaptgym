The Simulator as a Finite State Machine

The shape of every dialogue the simulator generates as a finite-state machine: what the user may say next, and which replies each turn can draw. This page is built from the machine's own code, so it cannot drift from it.

Stage 1 · The idea

What is a finite-state machine?

A fixed list of states, a rule for which input is allowed in each state, and what each input outputs and leads to. A turnstile is the classic case: a coin unlocks it, a push locks it again, and anything else changes nothing.

Ours works the same way. The state summarises a dialogue (which phase it is in, what the last reply demands, whether a wrong item was shown, what is listed, endorsed or selected). The input is a user turn and the output is the assistant's reply.

What it gives us

Consistency. The rules are a short table; the planner is a long procedure. Every generated plan is run through the table, so a plan that breaks a rule is rejected: after a question only an answer is allowed, after a wrong item only a rejection, a comparison only in dialogues that end successfully.

Coverage. The table lists all the turn and reply combinations that can occur. A test builds many plans and fails if one never appears, so an untested or unreachable branch cannot hide, and every state can still reach Done. This is transition coverage, not path coverage.

Not covered: the catalog (whether a partial item exists is the planner's call) and the wording a shopper model writes.
