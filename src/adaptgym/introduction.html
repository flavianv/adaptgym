The AdaptGym approach

Controlled conversations.
Measurable extraction.

A recommendation agent can understand the first request and still lose track of the user. What happens when a budget changes, a new requirement arrives, or “the second one” refers to an earlier recommendation?

AdaptGym tests whether a model can keep an accurate understanding of the user throughout a conversation. Code defines the intended changes and the reference state after each turn. An LLM expresses those changes naturally, a separate pass checks the wording, and the extractor is measured against the reference.

Control what changes. Measure what the model remembers. The same conversation–target pairs can support evaluation and supervised fine-tuning.

Available today: synthetic sessions, label checks and turn-by-turn extraction tests. Assistant actions are programmed. Training loops and evaluation of a live recommendation policy are proposed extensions.

What the tests reveal

One correct reply is not enough.

The reference state makes each expected update inspectable. A checkpoint can succeed at reading a new requirement while failing to preserve an earlier one.

Retain requirements

Keep an earlier constraint active across intervening turns, including when another field changes.

“Still under €120.”

Handle revisions

Replace an outdated value, add a new requirement, or remove a withdrawn constraint without losing unrelated information.

“Actually, make that €150.”

Resolve references

Interpret a short reply using the assistant question or displayed list that gives it meaning.

“The second one, but in blue.”

Track task boundaries

Recognize a new search or an explicitly completed task, and retire requirements that no longer apply.

“That’s sorted. Now I need running shoes.”

Separate needs from preferences

Distinguish what is mandatory for this search from a general preference that may matter again later.

“Usually remote; on-site is required this time.”

Vary conversation length, when requirements appear, and which events occur together to locate where performance breaks down. Planned success or failure endings describe the scenario; they do not score a live agent’s decisions.

Stage 1 · Evaluation

Control the data. Check the language. Measure the extraction.

  1. 01

    Procedurally generate intent traces

    Code samples what the user reveals and how their intent changes. Control the data distribution: number of turns, balance of scripted success and failure endings, and combinations of reveal, revision and other events. Compute the expected state after each turn.

  2. 02

    Convert traces into natural-looking sessions

    An LLM expresses the planned user events in natural language, around programmed assistant questions, recommendations and responses. Keep the intended transitions while varying how the user communicates them.

  3. 03

    Check that key information is preserved

    A separate LLM pass checks whether the visible conversation supports the intended labels. Flag missing information, weakened requirements or contradictions. A rejected example needs review or new wording before its labels can be trusted.

  4. 04

    Extract user information turn by turn

    The extraction model reads the conversation so far and updates a structured profile: short-term requirements for the current task and longer-term preferences. Choose accumulated state (its own previous valid prediction) or previous-correct-state conditioning. The current turn’s answer remains hidden.

  5. 05

    Compute extraction precision and recall

    Compare predictions with the per-turn reference states under explicit matching rules. Use per-field precision and recall, plus complete-turn coverage: were all expected values recovered? Group errors by field, conversation length, reveal pattern and ending, while declaring which matching rules the scores use.

Evaluate and improve extraction checkpoints. Controlled distributions make it possible to examine specific failure modes. The verified sessions and per-turn targets also provide supervision for fine-tuning; connecting them to a training pipeline remains further work.

Success and failure are scenario endings selected during generation. They are not measurements of a live recommendation agent’s performance. Model-assisted verification provides a check, rather than a guarantee, that the language preserves the labels.

What a scenario controls

Three questions behind every update.

How information is expressed, what a reply depends on, and how long a preference applies are separate dimensions. A conversation can combine them.

01 / EXPRESSION

How does the user convey it?

Explicit statements name a need directly. Implicit evidence conveys it through behavior or experience. Mixed conversations use both, within the attributes defined by the environment.

“I prefer lighter shoes.”
“The heavier pairs always stay in my cupboard.”

02 / INTERACTION

What does the reply depend on?

The user may volunteer a change, react with a self-contained correction, or give a reply that needs the assistant’s question or product list to make sense.

“My budget is €120.”
“The second one is too expensive.”

03 / TIME

How long does it apply?

A general preference can survive task completion. A requirement can apply only to the current search. Uncertain scope remains unresolved until the conversation provides enough evidence.

“I generally prefer remote work.”
“For this search, I need on-site work.”

Inspectable by design

Keep the evidence and the answer key distinct.

The extractor sees the schema, visible catalog information and conversation prefix. Accumulated mode supplies its own previous valid prediction, exposing error accumulation and recovery. Previous-correct-state mode supplies the reference state from the preceding turn to isolate the current update. Neither supplies the current or future answer.

Schema & catalog

Allowed attributes, values, units and operators, plus products or jobs that conform to them.

Personas & scenarios

General user background, sampled needs and scenario-defined changes.

Conversations & targets

Messages with stable identifiers and the expected intent after each user turn.

Audits & model traces

Support checks, evidence references, predictions and diagnostic scores.

The trace defines the intended meaning; the conversation must actually express it. A verifier checks that connection. It can still share the generator’s biases, especially when both use the same model family, so model approval does not replace human validation of dataset quality.

Three levels of evaluation

A supported label is only the first step.

DATA QUALITY

Does the conversation support its labels?

Check values, requirement strength, scope, outcomes and the messages that establish each claim.

INTENT QUALITY

Can the model maintain the right state?

Measure extraction after each user message. Keep validity, value coverage and stricter state diagnostics explicit so the score has a clear meaning.

DECISION QUALITY

Does that understanding improve the interaction?

Evaluate useful recommendations, clarifications and task outcomes. This downstream layer remains future work.

Related work

From synthetic conversations to better agents.

Spotify’s conversational recommendation work uses planned synthetic dialogues to test a live agent, followed by a loop that proposes prompt and tool improvements. Its study also reports human checks of the generated conversations and judge verdicts.

AdaptGym’s current focus is the intermediate representation: what the model believes the user wants after each turn. Procedural state transitions provide explicit extraction targets. Evaluating the usefulness of the agent’s decisions is a separate next stage.
