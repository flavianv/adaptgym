How each turn of a dialogue
is generated.

A turn is a user message plus the assistant reply to it. Click an outcome to trace its path and see a real line from a generated plan. The same turn structure is written as a finite-state machine and checked against every plan.

Before any text

The schedule is fixed first.

Opener1 turn. One hard group, plus any initial soft preferences.
Disclosure turnsOne per slot. Each has a kind: assistant_free, reactive_context or reactive_non_context, or reveal_dislike when requested.
Product actionsOptional: prefer, express_interest, withdraw_interest, select.
Finisher1 turn. Positive or negative.
slots = turns − 2 − len(product_actions)  ·  'mixed' uses each kind once while slots allow, draws the rest at random, then shuffles

Stage 2 · Assistant reply

What the assistant answers.

A ladder: the first rung whose condition holds decides the reply kind. The reply is built after the user's state is updated, and it looks ahead at what the next user turn must do.

Stage 3 · How they connect

Each reply constrains the next turn.

What the assistant does in reply i constrains what the user can say in turn i+1.

Private needs never appear in any user turn. They only decide which item can be the target. Unknown values count as a miss for soft needs and as a failure for hard needs. A dislike uses the ne operator ("not X"), which exists only for categorical attributes and never matches an unknown value.
